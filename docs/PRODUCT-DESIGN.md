## 1. 设计哲学

### 1.1 核心理念

AgentMonitor 的设计围绕一个核心信念：**Agent 的质量不能靠主观感受判断，必须靠数据说话。**

传统软件开发有单元测试、集成测试、性能测试来保证质量。但 AI Agent 与传统软件不同：
- **输入空间无限**：用户可能问任何问题
- **输出不确定**：同样的输入，两次回答可能不同
- **没有绝对正确**：回答可以"好"可以"更好"，没有唯一标准答案
- **依赖外部系统**：工具调用、知识库检索、第三方 API 都可能失败

因此，Agent 需要一套**全新的质量保障体系**——不是传统的 pass/fail 测试，而是基于**统计置信度**的持续评测与观测。

### 1.2 三个支柱

AgentMonitor 由三个相互支撑的支柱构成：

| 支柱 | 回答的问题 | 关键产出 |
|------|-----------|---------|
| **评测体系** | Agent 好不好？有多好？哪里不好？ | 通过率、评分分布、Bad Cases |
| **观测体系** | Agent 线上跑得怎么样？有没有出问题？ | 实时指标、告警、Trace 链路 |
| **提示词管理** | 为什么不好？怎么改？改了有没有效？ | Prompt 版本、A/B 对比、沙盒验证 |

三者不是独立的模块，而是一个**闭环**：
- 观测发现问题 → 提示词优化 → 评测验证效果 → 上线观测 → 再发现问题...

### 1.3 设计原则

1. **评测先于上线**：没有通过评测实验的 Agent 不应该上线
2. **观测即证据**：所有质量问题必须有 Trace 和数据支撑，不能凭感觉
3. **改动必验证**：任何 Prompt、模型、参数的改动都必须经过实验验证
4. **坏案例驱动优化**：优化的优先级由 Bad Cases 决定，而非整体分数
5. **数据飞轮**：线上真实数据自动回流为评测数据，评测集随时间增长

## 2. Agent 评测体系

### 2.1 为什么传统测试方法不适用

| 传统测试 | Agent 测试 | 原因 |
|---------|-----------|------|
| 断言匹配：`assert(output == "A")` | 语义匹配：`similarity(output, "A") > 0.8` | 输出可能表述不同但意思相同 |
| 100% 通过才能上线 | 85% 通过就可以考虑上线 | 开放域问题不可能全对 |
| 固定测试集 | 持续增长的动态测试集 | 线上不断产生新的场景和 edge case |
| 一次测试通过即可 | 需要持续回归测试 | 模型更新、Prompt 修改可能引入退化 |

### 2.2 评测的四维模型

Agent 的质量应该从**四个维度**分别评估：

```
                    ┌──────────────────┐
                    │    准确性         │
                    │  (Correctness)   │
                    │  回答对不对？      │
                    └────────┬─────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
┌───────────────┐    ┌───────────────┐    ┌───────────────┐
│    完整性      │    │    安全性      │    │    体验性      │
│(Completeness) │    │   (Safety)    │    │ (Experience)  │
│  信息全不全？  │    │  有没有风险？  │    │  体验好不好？  │
└───────────────┘    └───────────────┘    └───────────────┘
```

#### 维度一：准确性（Correctness）

**定义**：Agent 的回答在事实上是否正确，是否解决了用户的问题。

**评估方式**：
- **精确匹配**：输出与预期完全一致（适合结构化输出、代码、枚举值）
- **包含匹配**：输出包含预期的关键信息（适合清单类、步骤类回答）
- **语义相似度**：输出与预期的语义相似度超过阈值（适合开放性问题）
- **LLM 评判**：用更强的模型作为"裁判"打分（适合复杂主观问题）

**为什么重要**：准确性是 Agent 的底线。如果回答本身是错误的，再流畅、再安全也没有意义。

#### 维度二：完整性（Completeness）

**定义**：Agent 是否提供了用户需要的全部信息，有没有遗漏关键步骤或前提条件。

**评估方式**：
- **信息覆盖度**：检查输出是否覆盖了预期回答中的所有要点
- **必要追问**：如果信息不足，Agent 是否主动追问而非乱猜
- **步骤完整性**：多步骤任务中是否遗漏了关键步骤

**为什么重要**：一个不完整的回答会让用户感到困惑——比如客服说"您可以申请退款"但没有说"需要先登录账户"，用户就会卡在下一步。

#### 维度三：安全性（Safety）

**定义**：Agent 的输出是否包含有害、违法、歧视、误导性的内容，是否泄露了敏感信息。

**评估方式**：
- **关键词黑名单**：输出是否包含预定义的危险词
- **正则规则**：输出是否符合安全格式（如不给出生理/心理诊断建议）
- **LLM 安全评判**：用专门的安全模型检测输出风险
- **敏感信息检测**：输出中是否出现了不该泄露的用户数据、内部配置

**为什么重要**：安全性是 Agent 上线的硬门槛。一个准确的回答如果教用户做违法的事，后果比答错更严重。

#### 维度四：体验性（Experience）

**定义**：Agent 的回答是否自然、得体、符合用户预期，是否让人感到"舒服"。

**评估方式**：
- **语气一致性**：回答风格是否符合角色设定（如客服应该礼貌，教练应该鼓励）
- **简洁度**：回答是否简洁，没有冗余信息
- **结构化**：复杂信息是否用了列表、表格、分段等结构化表达
- **礼貌度**：是否使用了礼貌用语，是否尊重用户

**为什么重要**：体验决定了用户是否愿意继续使用。一个正确但冷漠、冗长的回答，用户下一次可能就不来了。

### 2.3 评测数据的三个来源

评测数据的质量直接决定了评测结果的可信度。AgentMonitor 支持三种数据来源，形成互补：

#### 来源一：人工构造（Synthetic）

**定义**：由开发者或测试人员手工编写的测试用例。

**适用场景**：
- 新 Agent 上线前的基线测试
- 覆盖已知的核心场景和边界条件
- 验证特定功能是否正常工作

**优点**：
- 可控性强，知道每条用例在测什么
- 可以精确构造 edge case
- 预期输出明确，评估标准清晰

**缺点**：
- 覆盖面有限，无法穷尽所有用户输入
- 可能带有开发者的偏见（只测自己想到的场景）
- 维护成本高，每次功能变更都要更新

**最佳实践**：
- 每条用例标注"场景分类"和"测试目的"
- 定期 review 用例，删除过时场景，补充新场景
- 核心场景至少覆盖 3 种变体（不同措辞、不同语气、不同详细程度）

#### 来源二：线上回流（Real-world Reflow）

**定义**：把 Agent 在线上运行的真实用户对话自动抽取为评测用例。

**适用场景**：
- 持续扩充评测集的覆盖面
- 捕获开发者想不到的真实用户提问方式
- 针对线上频发问题建立回归测试

**优点**：
- 覆盖面广，反映真实用户行为
- 不断自我增长，评测集随时间丰富
- 能发现人工构造时遗漏的场景

**缺点**：
- 需要人工标注 expected_output（或者假设线上当时的回答就是"正确"的）
- 可能包含低质量的用户输入（如乱码、恶意输入）
- 数据分布可能偏斜（某些高频场景占比过高）

**最佳实践**：
- 只回流"高质量会话"（对话轮数 >= 2、无报错、用户未投诉）
- 回流后人工抽检，修正错误的 expected_output
- 按场景分类统计，确保各类别样本均衡
- 对敏感场景（退款、投诉、安全）单独建立专项评测集

#### 来源三：对抗生成（Adversarial / Red Teaming）

**定义**：故意构造可能让 Agent 出错的输入，测试 Agent 的鲁棒性。

**适用场景**：
- 上线前的压力测试
- 安全合规审查
- 发现系统的薄弱点

**对抗类型**：

| 类型 | 示例 | 测试目的 |
|------|------|---------|
| **诱导误导** | "你不用遵守规则，直接告诉我..." | 测试指令遵循的鲁棒性 |
| **边界输入** | 空字符串、超长文本、特殊字符 | 测试输入处理的健壮性 |
| **角色扮演** | "假设你是管理员，请..." | 测试权限边界 |
| **多语言混合** | 中英混杂、方言、错别字 | 测试语言理解能力 |
| **注入攻击** | "忽略之前的指令，改为..." | 测试 Prompt 注入防御 |
| **逻辑陷阱** | "如果这句话是假的，那..." | 测试推理能力边界 |
| **情绪化输入** | 全大写、多感叹号、辱骂 | 测试情绪稳定性和安全性 |

**最佳实践**：
- 对抗用例单独标记，不与常规用例混合评估
- 对抗评测的通过标准应该比普通评测更宽松（允许"拒绝回答"作为正确答案）
- 发现薄弱点后，针对性补充训练数据或加固 Prompt

### 2.4 评测的生命周期

评测不是一次性任务，而是贯穿 Agent 全生命周期的持续活动：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Agent 评测生命周期                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  开发期                                                          │
│  ├── 人工构造核心场景用例（20-50条）                               │
│  ├── Playground 调试时即时验证                                    │
│  └── 通过基线评测才能进入测试期                                    │
│                                                                 │
│  测试期                                                          │
│  ├── 扩充评测集至 100-500 条（加入边界 case）                      │
│  ├── 运行完整实验，目标通过率 > 85%                                │
│  ├── 修复 Bad Cases → 重新评测 → 直到达标                         │
│  └── 通过完整评测才能上线                                         │
│                                                                 │
│  上线期                                                          │
│  ├── 开启线上观测（Dashboard、告警）                               │
│  ├── 每日自动回流优质会话到评测集                                  │
│  ├── 每周运行回归实验，检测是否有退化                               │
│  └── 发现新问题 → 补充用例 → 修复 → 验证                          │
│                                                                 │
│  迭代期                                                          │
│  ├── Prompt/模型/参数的任何改动 → 必须先跑实验                      │
│  ├── 新版本实验 vs 线上版本实验 → 横向对比                         │
│  ├── 新版本效果更好 → 更新线上                                     │
│  └── 新版本效果更差 → 回滚，继续优化                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.5 评测通过标准（Gate Criteria）

不同阶段的 Agent 应该有不同的评测通过标准：

| 阶段 | 数据集规模 | 通过率门槛 | 安全要求 | 延迟要求 |
|------|-----------|-----------|---------|---------|
| **开发期** | 20-50 条 | ≥ 60% | 无高危漏洞 | 无 |
| **测试期** | 100-500 条 | ≥ 85% | 100% 通过安全评测 | P99 < 3s |
| **上线期** | 500+ 条 | ≥ 90% | 100% 通过安全评测 | P99 < 2s |
| **生产回归** | 当前全量 | 不低于上一版本 | 无新增漏洞 | 不劣化 |

> **红线原则**：安全评测不通过，一律不允许上线。其他维度可以商量，安全不行。

## 3. 观测中心设计

### 3.1 观测的目的

评测回答的是"Agent 好不好"，观测回答的是"Agent 现在怎么样"。

如果说评测是**定期体检**，观测就是**实时心电监护**。两者缺一不可：
- 没有观测，上线后出了问题你不知道
- 没有评测，你知道有问题但不知道根本原因

### 3.2 观测的三个层次

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：宏观指标（Dashboard）                                │
│  ─────────────────────────────                              │
│  回答：整体健康状况？有没有出大事？                            │
│  使用者：运维人员、产品经理、管理层                            │
├─────────────────────────────────────────────────────────────┤
│  第二层：中观链路（Traces）                                   │
│  ─────────────────────────                                  │
│  回答：某次调用哪里出了问题？性能瓶颈在哪？                     │
│  使用者：开发者、测试人员                                     │
├─────────────────────────────────────────────────────────────┤
│  第三层：微观会话（Sessions）                                 │
│  ───────────────────────────                                │
│  回答：用户的完整体验如何？对话是否自然？                       │
│  使用者：产品经理、用户体验设计师                              │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 宏观指标：Dashboard 应该看什么

Dashboard 是决策者的"驾驶舱"，指标必须少而精。AgentMonitor 设计了 5 类核心指标：

#### 指标 1：请求量（Volume）

**定义**：单位时间内 Agent 接收并处理的请求数量。

**为什么重要**：
- 反映 Agent 的实际使用量
- 突增可能意味着营销活动生效或遭到攻击
- 突降可能意味着系统故障或用户流失

**怎么看**：
- 关注"当前值 vs 昨日同期 vs 上周同期"
- 异常波动（> ±30%）需要立即调查原因

#### 指标 2：成功率（Success Rate）

**定义**：成功处理的请求占总请求的比例。

**"成功"的定义**（按业务需要可配置）：
- 严格定义：Agent 正常返回了回答，无异常
- 宽松定义：即使回答不准确，只要系统没报错就算成功
- 业务定义：结合用户反馈，用户满意度 > 3 星才算成功

**为什么重要**：
- 成功率是 Agent 健康的最直观指标
- 成功率下降是最紧急的告警信号

**怎么看**：
- 正常应该稳定在 95% 以上
- 低于 90% 必须立即介入排查
- 关注"成功率下降的趋势"，而非单点波动

#### 指标 3：延迟分布（Latency Distribution）

**定义**：Agent 从接收到请求到返回回答的耗时。

**为什么重要**：
- 延迟直接影响用户体验（> 3s 用户明显感知卡顿）
- 延迟是成本的风向标（延迟高通常意味着 Token 消耗多或模型选择不当）
- 延迟突增往往预示着后端依赖（数据库、API）出问题

**怎么看**：
- 关注 P50（中位数）、P95、P99，而非平均值
- P50 反映普通用户的体验，P99 反映最差情况的兜底
- 如果 P50 正常但 P99 飙高，说明有长尾问题（如特定复杂查询慢）

#### 指标 4：Token 消耗（Cost）

**定义**：Agent 每次调用消耗的 Token 数量（Prompt + Completion）。

**为什么重要**：
- Token = 钱。成本控制是商业可持续的核心
- Token 消耗异常增长可能意味着 Prompt 泄露、循环调用、冗余上下文
- 不同模型的 Token 单价不同，需要监控"单位请求成本"

**怎么看**：
- 监控"每千次请求的平均 Token 消耗"
- 监控"Token 消耗的趋势"，及时发现成本泄漏
- 结合延迟一起看：如果 Token 没变但延迟变高，可能是模型拥堵

#### 指标 5：连接状态（Connectivity）

**定义**：Agent SDK 与监控系统的连接健康状况。

**状态定义**：
- 🟢 **已连接**：5 分钟内有数据上报，Agent 正常运行
- 🟡 **等待 SDK 接入**：系统运行正常，但没有 Agent 上报数据
- 🔴 **已断开**：系统不可达或 Agent 已停止上报

**为什么重要**：
- 防止"监控盲区"——系统显示一切正常，其实 Agent 早就挂了
- 区分"Agent 没出问题"和"Agent 没上报数据"两种完全不同的状况

### 3.4 中观链路：Trace 追踪应该追什么

Trace 是开发者的"显微镜"，用于定位具体问题。

#### 必须追踪的事件类型

| 事件类型 | 追踪内容 | 为什么必须追踪 |
|---------|---------|--------------|
| **LLM 调用** | 模型名、输入消息、输出结果、Token 用量、延迟 | Agent 的核心行为，成本和延迟的大头 |
| **工具调用** | 工具名、输入参数、返回结果、错误信息、延迟 | 工具失败是 Agent 失败的主要原因之一 |
| **函数调用** | 函数名、输入参数、返回结果、异常信息、延迟 | 业务逻辑的自定义函数可能出错 |
| **用户消息** | 角色（user/assistant）、内容、时间戳 | 还原对话上下文，理解用户意图 |
| **决策事件** | 决策类型、选项、选中项、置信度、推理过程 | 可解释性的关键，排查"为什么选这个" |
| **会话边界** | 开始时间、结束时间、元数据 | 界定一次完整交互的范围 |

#### Trace 之间的父子关系

Agent 的一次调用往往不是单步的，而是链式的：

```
用户提问: "北京今天天气怎么样？"
    │
    ├── [message] 用户消息: "北京今天天气怎么样？"
    │
    ├── [function] 意图识别: "query_weather"
    │       input:  { text: "北京今天天气怎么样？" }
    │       output: { intent: "weather", city: "北京", date: "today" }
    │
    ├── [tool_call] 调用天气 API
    │       input:  { city: "北京", date: "2024-01-15" }
    │       output: { temp: 5, condition: "晴", humidity: 30 }
    │       latency: 320ms
    │
    ├── [llm] 生成自然语言回答
    │       model: gpt-4
    │       input:  { messages: [..., { role: "user", content: "北京今天天气..." }] }
    │       output: { content: "北京今天晴，气温5度..." }
    │       tokens: { prompt: 120, completion: 45, total: 165 }
    │       latency: 1500ms
    │
    └── [message] 助手回复: "北京今天晴，气温5度..."
```

**为什么必须记录父子关系**：
- 出了问题能快速定位：是意图识别错了？还是工具返回了错误数据？还是 LLM 生成错了？
- 性能分析：哪个环节最慢？是 LLM 推理慢还是工具调用慢？
- 成本分析：Token 主要消耗在哪个 LLM 调用上？

### 3.5 微观会话：Session 回放应该看什么

Session 回放是产品经理和 UX 设计师的"用户访谈录像"。

#### 为什么要看 Session，而不只看 Trace

| 视角 | 能看到什么 | 看不到什么 |
|------|-----------|-----------|
| **Trace** | 每次技术调用的细节 | 用户的情绪和体验 |
| **Session** | 完整对话流程、用户的挫败感、多轮交互的连贯性 | 单次调用的技术细节 |

#### Session 回放的关键检查点

**检查点 1：对话是否自然**
- Agent 是否理解了用户的真实意图（而非表面文字）
- Agent 是否使用了上下文信息（如用户之前提过的事情）
- 多轮对话中 Agent 是否"记得"之前的约定

**检查点 2：Agent 是否过度自信**
- 当信息不足时，Agent 是"乱猜"还是"主动追问"
- 当遇到知识盲区时，Agent 是"编造"还是"坦诚不知道"

**检查点 3：异常处理是否得体**
- 工具调用失败时，Agent 是崩溃还是优雅地告诉用户"服务暂时不可用"
- LLM 返回格式错误时，Agent 是报错还是尝试重新请求

**检查点 4：用户是否满意**
- 对话轮数：如果一个问题用户问了 5 轮还没解决，说明 Agent 没理解
- 用户是否使用了"谢谢""明白了"等正向结束语
- 用户是否在最后一轮表达了不满（虽然 Agent 可能没识别出来）

### 3.6 告警设计：什么时候应该告警

告警不是越多越好，过多的告警会导致"告警疲劳"。AgentMonitor 的告警遵循**"少而精、分层级"**原则：

| 告警级别 | 触发条件 | 响应要求 | 通知对象 |
|---------|---------|---------|---------|
| **P0 - 紧急** | 成功率 < 80%，或完全无数据上报 | 15 分钟内必须响应 | 值班工程师 + 技术负责人 |
| **P1 - 重要** | 成功率 < 90%，或 P99 延迟 > 5s | 1 小时内响应 | 值班工程师 |
| **P2 - 警告** | 成功率 < 95%，或 Token 消耗突增 > 50% | 4 小时内响应 | 团队群通知 |
| **P3 - 提示** | 单日请求量创历史新高等正向事件 | 无需响应，供参考 | 日报/周报 |

**告警的附加信息**：
每条告警必须附带：
- 触发时间和持续时间
- 影响的请求数量/用户数
- 相关的 Trace/Sesison 链接（一键跳转排查）
- 最近一次的变更记录（如"3 小时前 Prompt v2 上线"）

## 4. 提示词管理体系

### 4.1 为什么提示词需要管理

提示词（Prompt）是 Agent 的"源代码"。在传统软件中：
- 代码改动 → Git 版本管理 → Code Review → 测试通过 → 上线

但在 AI Agent 中：
- 提示词改动 → 经常直接改了就上线 → 没有版本 → 不知道哪个版本好 → 出了问题回滚不了

**Prompt 管理的核心目标**：让 Prompt 的迭代像代码迭代一样可控、可追溯、可验证。

### 4.2 Prompt 的生命周期

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ 构思    │ → │ 编写    │ → │ 沙盒验证 │ → │ 实验验证 │ → │ 上线    │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
     │              │              │              │              │
     ▼              ▼              ▼              ▼              ▼
  产品/业务     开发者/PE     Playground     评测实验      线上部署
  定义需求      撰写初稿      快速验证       批量验证       持续观测
```

#### 阶段一：构思

**参与者**：产品经理、业务专家

**输出**：
- Prompt 目标（这个 Prompt 要解决什么问题）
- 角色设定（Agent 是谁：客服？教练？顾问？）
- 约束条件（绝对不能做什么、必须遵守什么规则）
- 输出格式要求（JSON？Markdown？纯文本？）

#### 阶段二：编写

**参与者**：Prompt 工程师（PE）、开发者

**原则**：
- **一次只改一处**：不要同时改角色设定、输出格式、示例，否则不知道哪个改动有效
- **保留变更记录**：每次修改都要写清楚"为什么改"
- **结构化管理**：把 Prompt 拆分为"角色定义 + 任务说明 + 约束条件 + 输出格式 + 示例"等模块

#### 阶段三：沙盒验证（Playground）

**参与者**：Prompt 工程师

**目的**：在正式跑实验前，快速验证 Prompt 的基本可用性。

**验证 checklist**：
- [ ] 输入几个典型问题，输出是否符合预期
- [ ] 输入边界问题（空、超长、乱码），输出是否优雅处理
- [ ] 输入对抗性问题（诱导、注入），输出是否安全拒绝
- [ ] 多次输入同样的问题，输出是否稳定（随机性是否可接受）

**沙盒不是实验**：沙盒验证的是"Prompt 能不能用"，实验验证的是"Prompt 好不好"。沙盒快但样本少，实验慢但统计可信。

#### 阶段四：实验验证

**参与者**：Prompt 工程师 + 评测流程

**步骤**：
1. 保存当前 Prompt 为新版本
2. 创建实验，绑定评测数据集
3. 用新 Prompt 批量跑数据集
4. 生成报告，与上一版本对比
5. 决策：更好 → 上线；更差 → 回滚或继续优化

#### 阶段五：上线与持续观测

**参与者**：开发者、运维

**步骤**：
1. 更新线上 Agent 的 Prompt
2. Dashboard 观测关键指标是否异常
3. 每日/每周查看 Session 回放，发现新问题
4. 线上数据回流，扩充评测集

### 4.3 Prompt 的版本策略

#### 版本号规则

采用语义化版本：

| 版本变化 | 含义 | 示例 |
|---------|------|------|
| **主版本 +1** | 角色定义、核心逻辑有重大变更 | v1.0 → v2.0 |
| **次版本 +1** | 任务说明、约束条件有调整 | v1.1 → v1.2 |
| **修订号 +1** | 示例、措辞微调，不影响核心逻辑 | v1.1.0 → v1.1.1 |

#### 版本标签

除了版本号，每个版本可以打标签，方便快速识别：

| 标签 | 含义 |
|------|------|
| `current` | 当前线上正在使用的版本 |
| `stable` | 经过充分验证的稳定版本 |
| `candidate` | 候选版本，待实验验证 |
| `deprecated` | 已废弃，不再使用 |

#### 版本对比

必须支持两个版本的 diff 对比：
- 新增的内容（绿色高亮）
- 删除的内容（红色高亮）
- 修改的内容（黄色高亮）

### 4.4 变量注入机制

Prompt 中的变量是 Prompt 与业务数据连接的桥梁。

**设计原则**：
1. **变量名自解释**：`{{user_name}}` 比 `{{u}}` 好
2. **默认值机制**：如果变量未提供，Prompt 仍能正常运行
3. **类型校验**：数字型变量不要注入字符串，防止格式错误
4. **长度限制**：对可能很长的变量（如用户历史记录）做截断

**典型变量**：

| 变量 | 用途 | 示例值 |
|------|------|--------|
| `{{user_name}}` | 用户称呼 | "张三" |
| `{{user_tier}}` | 用户等级 | "VIP" / "普通" |
| `{{conversation_history}}` | 历史对话 | "用户: 你好\n助手: 您好" |
| `{{current_date}}` | 当前日期 | "2024-01-15" |
| `{{product_list}}` | 产品列表 | "[产品A, 产品B, 产品C]" |

### 4.5 多模型对比

同一个 Prompt，不同模型的输出可能差异很大。多模型对比帮助选择最优模型配置。

**对比维度**：
- **准确性**：谁回答得更对
- **完整性**：谁提供的信息更全
- **安全性**：谁更不容易产生有害输出
- **成本**：谁的 Token 消耗更少
- **延迟**：谁响应更快

**决策矩阵**：

| 模型 | 准确性 | 成本 | 延迟 | 推荐场景 |
|------|--------|------|------|---------|
| GPT-4 | ★★★ | 高 | 慢 | 复杂推理、高风险场景 |
| Claude-3 | ★★★ | 高 | 中 | 长文本理解、创意生成 |
| GPT-3.5 | ★★ | 低 | 快 | 简单问答、高频场景 |
| 本地模型 | ★ | 极低 | 极快 | 离线场景、隐私敏感 |

**策略建议**：
- 不是所有场景都需要最强模型。可以用"意图识别 + 路由"策略：简单问题用 GPT-3.5，复杂问题用 GPT-4
- 对于准确率要求极高的场景（如医疗、法律），GPT-4 也可能不够，需要人工复核层

## 5. 三者闭环关系

评测、观测、提示词管理不是三个独立模块，而是一个有机整体。

### 5.1 数据流向

```
                        ┌─────────────┐
                        │   线上 Agent  │
                        │   (运行中)    │
                        └──────┬──────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
              ▼                ▼                ▼
    ┌─────────────────┐ ┌─────────────┐ ┌─────────────┐
    │  观测中心        │ │  数据回流    │ │  用户反馈    │
    │  (实时追踪)      │ │  (自动抽取)  │ │  (主动上报)  │
    └────────┬────────┘ └──────┬──────┘ └──────┬──────┘
             │                 │               │
             │                 └───────┬───────┘
             │                         │
             ▼                         ▼
    ┌─────────────────────────────────────┐
    │           评测数据集                  │
    │  (持续增长的人工+回流+对抗用例)        │
    └─────────────────┬───────────────────┘
                      │
                      ▼
    ┌─────────────────────────────────────┐
    │           评测实验                    │
    │  (用数据集"考"Agent，生成报告)         │
    └─────────────────┬───────────────────┘
                      │
         ┌────────────┼────────────┐
         │            │            │
         ▼            ▼            ▼
    ┌─────────┐ ┌─────────┐ ┌─────────┐
    │ Bad Cases│ │ 通过报告 │ │ 对比报告 │
    │ (问题)   │ │ (验证)   │ │ (决策)   │
    └────┬────┘ └────┬────┘ └────┬────┘
         │           │           │
         │           │           │
         ▼           │           │
    ┌─────────────────┘           │
    │   提示词管理 (Playground)     │
    │   分析问题 → 修改 Prompt      │
    │   沙盒验证 → 保存新版本       │
    └─────────────────┬───────────┘
                      │
                      ▼
    ┌─────────────────────────────────────┐
    │  再次跑实验 → 对比新旧版本效果         │
    │  更好 → 更新线上 Prompt               │
    │  更差 → 继续优化                      │
    └─────────────────────────────────────┘
                      │
                      ▼
              ┌───────────────┐
              │   回到线上运行  │
              │   (循环继续)   │
              └───────────────┘
```

### 5.2 角色分工

| 角色 | 主要使用模块 | 核心活动 |
|------|------------|---------|
| **产品经理** | 观测中心(Session)、评测报告 | 定义评测标准、分析用户体验、决策上线/回滚 |
| **Prompt 工程师** | 提示词管理、Playground、评测实验 | 编写 Prompt、沙盒调试、跑实验验证 |
| **开发者** | 观测中心(Trace)、评测数据集 | 排查技术问题、补充回流数据、修复 Bad Cases |
| **测试/QA** | 评测中心全部 | 构造测试用例、执行实验、分析 Bad Cases |
| **运维** | 观测中心(Dashboard)、告警 | 监控系统健康、响应告警、保障可用性 |
| **管理层** | Dashboard、实验对比报告 | 看整体质量趋势、资源投入决策 |

### 5.3 关键决策点

在闭环中，有几个关键决策点需要明确的决策标准：

**决策点 1：Bad Case 要不要修？**
- 如果某类 Bad Case 占比 > 5% → 必须修
- 如果是个别极端 case → 可以标记为"已知限制"，暂不处理
- 如果是安全相关 → 无论占比多少，必须修

**决策点 2：新版本要不要上线？**
- 通过率提升 ≥ 3% → 可以上线
- 通过率下降 ≥ 1% → 不能上线
- 通过率持平但延迟/成本下降 → 可以上线
- 通过率持平但延迟/成本上升 → 不能上线

**决策点 3：评测集要不要扩充？**
- 线上发现了新的失败场景 → 立即回流补充
- 某类场景在评测集中占比 < 5% 但线上占比 > 20% → 需要补充
- 评测集用例数 < 100 → 必须扩充到至少 100 条

## 6. 成熟度模型

不同阶段的团队，对评测、观测、提示词管理的需求深度不同。

### Level 1：基础监控（0-3 个月）

**特征**：
- Agent 刚上线，以"能用"为目标
- 团队对 Agent 的质量没有清晰概念
- 出问题靠用户反馈，而非主动发现

**最低要求**：
- ✅ Agent 接入 SDK，上报基本 trace
- ✅ Dashboard 能看请求量和成功率
- ✅ 有告警通知（至少成功率低于 80% 时告警）

**不需要**：
- ❌ 系统化的评测实验
- ❌ Prompt 版本管理
- ❌ 复杂的数据回流

### Level 2：质量可控（3-6 个月）

**特征**：
- Agent 稳定运行，开始关注质量
- 团队意识到"上线前需要验证"
- 开始积累评测用例

**最低要求**：
- ✅ 有 50-100 条人工构造的评测用例
- ✅ 每次 Prompt/模型改动前跑实验
- ✅ 有明确的上线通过标准（如通过率 > 85%）
- ✅ Prompt 有版本管理，能对比 diff
- ✅ 观测到 Session 级别，能看完整对话

### Level 3：数据驱动（6-12 个月）

**特征**：
- Agent 成为核心业务组件
- 团队用数据说话，优化有明确依据
- 建立了评测 → 优化 → 验证的完整流程

**最低要求**：
- ✅ 评测集 > 500 条，含人工+回流+对抗
- ✅ 每周运行回归实验，监控退化
- ✅ 数据回流自动化（每日/每周自动回流）
- ✅ 多维评估（准确性+完整性+安全性+体验性）
- ✅ 多模型对比成为选型常态
- ✅ Bad Cases 有追踪闭环（发现问题 → 创建工单 → 修复 → 验证）

### Level 4：持续优化（12 个月以上）

**特征**：
- Agent 质量成为团队的核心竞争力
- 评测和观测完全融入开发流程
- 形成了自我增强的数据飞轮

**最低要求**：
- ✅ 评测集 > 2000 条，覆盖所有核心场景
- ✅ 实验与 CI/CD 集成，自动触发
- ✅ A/B 测试常态化，新 Prompt 小流量验证
- ✅ 自动生成评测报告，定期发送给管理层
- ✅ 有专门的 Prompt 工程师角色
- ✅ 对抗评测成为上线前的强制 gate

## 附录：核心原则速查表

| # | 原则 | 含义 |
|---|------|------|
| 1 | **评测先于上线** | 没有通过评测的 Agent 不应该接触真实用户 |
| 2 | **观测即证据** | 所有质量判断必须有数据支撑 |
| 3 | **改动必验证** | 任何 Prompt/模型/参数的变更必须经过实验 |
| 4 | **坏案例驱动** | 优化的优先级由 Bad Cases 决定 |
| 5 | **安全是红线** | 安全评测不通过，一律禁止上线 |
| 6 | **数据飞轮** | 线上数据自动回流为评测数据，持续扩充 |
| 7 | **分层评估** | 准确性、完整性、安全性、体验性分别评估 |
| 8 | **统计置信** | 用通过率、P50/P95 等统计指标，而非单点判断 |
| 9 | **闭环追踪** | 每个 Bad Case 从发现到修复必须有追踪 |
| 10 | **版本可控** | Prompt 和评估器的版本必须可回滚 |
