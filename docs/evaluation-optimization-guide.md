# AgentMonitor 评测优化功能使用指南

> 本文档介绍 AgentMonitor 平台中 **Prompt 评测与 AI 自动优化** 功能的完整使用方法，涵盖数据集管理、评估器配置、评测实验执行、AI 辅助调优、回归测试等核心能力。

---

## 一、功能介绍

AgentMonitor 的评测优化模块是一套**从评测到优化的完整闭环工具链**，帮助开发者：

1. **系统性地评测 Prompt 质量** —— 用真实用例批量测试，获得量化的评分报告
2. **AI 辅助自动优化 Prompt** —— 基于低分样本的失败模式，自动生成改进建议
3. **追踪 Prompt 版本演进** —— 每次修改自动保存版本，支持一键回滚
4. **防止回归** —— 保存新版本时自动跑回归实验，确保改进不会破坏已有能力
5. **持续监控** —— 定时自动评测生产环境的 Agent 表现

### 核心能力一览

| 能力 | 说明 |
|------|------|
| **数据集管理** | 创建测试用例集合，支持从 Session/Trace 自动回流数据 |
| **评估器模板** | 12 种内置评估器（精确匹配、LLM 裁判、正则、语义相似度等） |
| **评测实验** | 批量运行 Prompt + 模型，自动评分并生成报告 |
| **AI Prompt 调优** | 分析失败用例，自动生成优化后的 Prompt 和改进说明 |
| **回归测试** | 保存 Prompt 版本时自动创建对比实验 |
| **结果校准** | 人工修正 AI 评估器的误判，提升评估准确性 |
| **自动评测任务** | 定时抽样评测生产 Trace，持续监控质量 |
| **实验对比** | 多个实验横向对比，直观看出哪个版本更好 |
| **Playground 快速测试** | 单条输入快速验证 Prompt 效果 |

## 二、核心概念

### 2.1 数据集（Dataset）

数据集是一组**测试用例**的集合，每个用例包含：
- `input`：输入给 Agent 的问题/指令（必填）
- `expected_output`：期望的标准答案（可选，用于评分参考）
- `fields`：额外字段（可选）

**数据集类型**：
- `qa`：问答类（适合精确匹配、准确性评估）
- `chat`：对话类（适合语义相似度、安全性评估）
- `custom`：自定义（通用）

### 2.2 评估器（Evaluator）

评估器定义了**如何给模型输出打分**。AgentMonitor 内置 5 种评估类型：

| 类型 | 原理 | 适用场景 |
|------|------|---------|
| `exact_match` | 输出与期望完全一致 | 确定性问答、数学计算 |
| `contains` | 输出包含期望的关键内容 | 信息抽取、关键词检查 |
| `similarity` | 语义相似度计算 | 开放式问答、创意生成 |
| `regex` | 正则匹配 | 格式验证、安全规则检查 |
| `llm_judge` | 用大模型当裁判打分 | 复杂质量评估（准确性、安全性、简洁性等） |

**内置模板**（12 种）：
- 精确匹配评估器、包含匹配评估器、语义相似度评估器
- LLM 准确性评估器、LLM 安全性评估器、LLM 简洁性评估器
- 正则安全检测器、JSON 格式验证器
- 关键词黑名单检测器、长度约束检查器
- 代码质量评估器、指令遵循度评估器

### 2.3 评测实验（Evaluation Experiment）

实验是**一次完整的批量评测过程**，包含：
- 关联的 Prompt（可选）
- 测试数据集
- 目标模型配置
- 运行配置（temperature、max_tokens、timeout_ms）
- 实验结果（每条用例的得分、输出、延迟）

实验执行流程：
```
创建实验 → 运行实验 → 逐条调用目标模型 → 评估器打分 → 生成报告
```

### 2.4 Prompt 版本（Prompt Version）

每次修改 Prompt 内容或配置时，系统会自动创建一个新版本，记录：
- 版本号（v1, v2, v3...）
- 修改内容
- 修改说明
- 时间戳

支持**一键回滚**到任意历史版本。

### 2.5 配置合并优先级

当调用目标模型时，配置按以下优先级合并：

```
实验级 runConfig（运行时配置）> Prompt 级 config（Prompt 配置）> 硬编码默认值
```

Prompt 级配置示例（JSON，支持注释）：
```json
{
  // 控制输出随机性: 0=确定性, 1=随机
  "temperature": 0.7,
  // 最大输出 token 数
  "max_tokens": 2048,
  // 模型调用超时毫秒数
  "timeout_ms": 30000
}
```

## 三、功能用法

### 3.1 前置准备

1. **配置模型**：在「模型配置」页面添加至少一个模型（支持 OpenAI、Anthropic、DeepSeek、豆包、小米 MiMo 等）
2. **创建 Prompt**：在「Prompt 管理」页面创建 Prompt，填写内容和配置选项
3. **创建数据集**：在「评测中心」→「数据集」页面创建数据集并添加用例

### 3.2 创建评测实验

**路径**：评测中心 → 实验 → 新建实验

**步骤**：
1. 填写实验名称和描述
2. 选择**数据集**（必须）
3. 选择**Prompt**（可选，不选则直接传输入给模型）
4. 选择**目标模型配置**（必须）
5. 填写运行配置（可选，覆盖 Prompt 级配置）
6. 点击「创建并运行」

**实验状态**：
- `pending`：待运行
- `running`：运行中
- `completed`：已完成（可查看报告和优化）
- `failed`：失败

### 3.3 查看实验报告

实验完成后，点击实验卡片查看详细报告：

- **总览**：总用例数、通过数、失败数、通过率、平均分、平均延迟
- **分数分布**：各分数段的用例数量柱状图
- **延迟分布**：0-500ms / 500-1000ms / 1000-2000ms / 2000ms+
- **失败用例**：低分样本的输入、输出、期望输出、评分理由
- **结果校准**：对 AI 评估器的误判进行人工修正

### 3.4 AI 辅助 Prompt 调优

**前提**：实验状态为 `completed`，且存在低分样本（score < 0.6）

**路径**：Prompt 管理 → 选择一个 Prompt → 「AI 调优」标签

**步骤**：
1. 选择一个已完成的评测实验
2. 选择用于优化的模型（默认使用项目下第一个有 API Key 的模型）
3. 点击「生成优化建议」
4. 系统分析失败用例的模式，返回：
   - **优化后 Prompt**：改进后的完整 Prompt 内容
   - **改动说明**：具体修改了哪些地方
   - **优化理由**：分析失败原因和改进逻辑
   - **低分样本详情**：失败的用例列表
5. 满意后点击「应用优化」，自动创建新版本

### 3.5 保存 Prompt 版本与回归测试

**路径**：Prompt 管理 → 编辑 Prompt → 勾选「保存时创建回归实验」

**步骤**：
1. 修改 Prompt 内容或配置
2. 勾选「自动回归测试」
3. 选择回归数据集
4. 保存后系统自动：
   - 创建新版本（vN+1）
   - 创建回归实验并运行
   - 对比新旧版本的表现

### 3.6 实验对比

在「评测中心」选择多个实验，点击「对比」按钮，可查看：
- 各实验的通过率、平均分、延迟对比
- 直观判断哪个 Prompt 版本/模型配置更优

### 3.7 Playground 快速测试

**路径**：Prompt 管理 → 选择一个 Prompt → 「Playground」标签

用于单条输入快速验证 Prompt 效果，支持：
- 选择模型配置
- 实时查看输出和 Token 用量
- 运行历史记录

## 四、适用场景

| 场景 | 描述 | 推荐评估器 |
|------|------|-----------|
| **Prompt 迭代优化** | 持续改进 Prompt 质量，确保每次修改都有数据支撑 | llm_judge + exact_match |
| **模型选型对比** | 同一 Prompt 用不同模型跑，选出最优模型 | 任意 |
| **回归测试** | 新功能开发后，验证旧能力未被破坏 | exact_match / contains |
| **生产质量监控** | 定时抽样评测线上 Agent 输出质量 | llm_judge + regex |
| **数据集构建** | 从真实 Session/Trace 回流数据，构建评测集 | — |
| **A/B 测试** | 两个 Prompt 版本并行对比 | 任意 |

## 五、场景用法教程

### 场景一：Prompt 迭代优化（最常用）

**目标**：通过评测发现 Prompt 弱点，用 AI 自动优化，形成「评测→优化→验证」闭环。

**步骤**：

1. **创建 Prompt**
   - 进入「Prompt 管理」→「新建 Prompt」
   - 名称：`客服问候语`
   - 内容：`你是一位专业的客服代表。请用友好的语气回复用户的问题。`
   - 配置选项：`{"temperature": 0.7, "max_tokens": 200}`

2. **创建数据集**
   - 进入「评测中心」→「数据集」→「新建数据集」
   - 名称：`客服场景测试集`
   - 类型：`chat`
   - 添加用例：
     | input | expected_output |
     |-------|-----------------|
     | 你好，我想退货 | 您好！很抱歉给您带来不便，请提供订单号... |
     | 这个产品质量太差了 | 非常抱歉听到您的反馈，我们非常重视产品质量... |
     | 怎么联系人工客服 | 您可以通过以下方式联系我们的客服团队... |

3. **创建评估器**
   - 进入「评测中心」→「评估器」→「从模板创建」
   - 选择「LLM 准确性评估器」+「指令遵循度评估器」
   - 或选择「语义相似度评估器」作为快速基准

4. **创建并运行实验**
   - 进入「评测中心」→「实验」→「新建实验」
   - 选择 Prompt：`客服问候语`
   - 选择数据集：`客服场景测试集`
   - 选择目标模型：已配置的模型（如 GPT-4o）
   - 点击「创建并运行」
   - 等待实验完成（状态变为 `completed`）

5. **查看报告**
   - 点击实验卡片查看报告
   - 假设结果：avg_score = 0.55，case1 = 0.85, case2 = 0.4, case3 = 0.4
   - 分析：case2 和 case3 得分低，模型处理负面反馈和引导转人工时表现不佳

6. **AI 调优**
   - 回到「Prompt 管理」→ 选择 `客服问候语` →「AI 调优」标签
   - 选择上一步完成的实验
   - 点击「生成优化建议」
   - 系统分析失败模式后返回优化建议：
     - 优化后 Prompt：增加了处理负面情绪的专门指令、增加了转人工流程说明
     - 改动说明：`["增加了负面情绪安抚话术", "增加了转人工的明确引导"]`
     - 优化理由：低分样本主要失败在处理用户不满情绪和引导转人工时缺乏结构化回复
   - 点击「应用优化」，自动创建 v2 版本

7. **验证优化效果**
   - 用 v2 版本重新创建实验
   - 对比 v1 和 v2 的报告，确认 avg_score 提升

---

### 场景二：模型选型对比

**目标**：同一 Prompt 用多个模型跑，选出性价比最高的模型。

**步骤**：

1. 在「模型配置」页面配置多个模型（如 GPT-4o、DeepSeek-V3、MiMo-v2.5）

2. 创建一个 Prompt 和数据集

3. 创建多个实验，**只有目标模型不同**：
   - 实验 A：Prompt + 数据集 + GPT-4o
   - 实验 B：Prompt + 数据集 + DeepSeek-V3
   - 实验 C：Prompt + 数据集 + MiMo-v2.5

4. 全部运行完成后，进入「评测中心」→ 勾选三个实验 →「对比」

5. 对比维度：
   - 平均分：哪个模型更准？
   - 延迟：哪个模型更快？
   - 通过率：哪个模型更稳定？

6. 根据业务需求选择最优模型（如追求速度选延迟最低的，追求质量选分数最高的）

---

### 场景三：回归测试（防止能力退化）

**目标**：Prompt 修改后，自动验证旧能力没有被破坏。

**步骤**：

1. **准备回归数据集**
   - 选择覆盖核心能力的 20-50 条用例
   - 这些用例代表当前 Prompt 已经能正确处理的场景

2. **编辑 Prompt**
   - 进入「Prompt 管理」→ 编辑现有 Prompt
   - 修改内容（如增加新场景的指令）
   - 勾选「保存时创建回归实验」
   - 选择回归数据集
   - 保存

3. **查看回归结果**
   - 系统自动创建并运行回归实验
   - 对比新旧版本的通过率
   - 如果新版本通过率下降，说明修改破坏了旧能力，考虑回滚

4. **一键回滚**
   - 如果新版本表现不佳，进入 Prompt 的「版本」标签
   - 找到上一个版本，点击「回滚」

---

### 场景四：生产质量监控（自动评测）

**目标**：定时自动抽样评测线上 Agent 的输出质量，及时发现异常。

**步骤**：

1. **创建监控数据集**
   - 从历史 Session/Trace 中回流真实用户问题
   - 进入「评测中心」→「数据集」→ 选择一个数据集
   - 点击「从 Session 回流」或「从 Trace 回流」
   - 选择时间段和 Session/Trace，系统自动提取 input/output 作为用例

2. **配置评估器**
   - 选择「LLM 安全性评估器」检查有害内容
   - 选择「关键词黑名单检测器」检查敏感词泄露
   - 选择「LLM 准确性评估器」检查回答质量

3. **创建自动评测任务**
   - 进入「评测中心」→「自动评测」→「新建任务」
   - 名称：`每日质量抽检`
   - 选择监控数据集
   - 选择评估器
   - 设置执行间隔：24 小时
   - 设置抽样数量：10 条
   - 启用任务

4. **查看监控结果**
   - 任务每次运行后会生成实验
   - 在「实验」页面查看历史趋势
   - 如果某天的平均分显著下降，及时排查问题

---

### 场景五：从真实数据构建评测集

**目标**：利用线上真实对话，快速构建高质量的评测数据集。

**步骤**：

1. **观测中心数据回流**
   - 进入「观测中心」→「Sessions」
   - 找到一个用户对话质量较高的 Session
   - 点击「回流到数据集」
   - 选择目标数据集（或新建）
   - 系统自动提取 user/assistant 消息对作为 input/expected_output

2. **Trace 数据回流**
   - 进入「观测中心」→「Traces」
   - 过滤特定类型的 Trace（如 `llm_call`）
   - 选择多个 Trace，点击「批量回流」
   - 系统自动提取 input/output 作为用例

3. **人工审核**
   - 进入数据集详情页
   - 检查回流的数据，修正 expected_output
   - 删除质量不高的用例

4. **打标签（可选）**
   - 为不同用例添加 `fields` 标签（如 `category: 投诉`, `difficulty: 困难`）
   - 便于后续按维度分析实验结果

---

### 场景六：A/B 测试（两个 Prompt 版本对比）

**目标**：科学对比两个 Prompt 版本的效果，用数据说话。

**步骤**：

1. **准备两个版本**
   - 版本 A：当前线上 Prompt（v1）
   - 版本 B：改进后的 Prompt（v2）

2. **创建对比实验**
   - 实验 A：v1 + 数据集 + 模型 X
   - 实验 B：v2 + 同个数据集 + 同一个模型 X
   **注意**：只改变 Prompt，其他变量保持一致

3. **运行并对比**
   - 两个实验都运行完成后
   - 勾选两个实验 →「对比」
   - 查看各维度差异

4. **决策**
   - 如果 v2 平均分更高 + 延迟不增加 → 推广 v2
   - 如果 v2 某类用例表现下降 → 针对性优化
   - 如果差异不大 → 考虑延迟/成本等其他因素

---

### 场景七：结果校准（修正 AI 评估误判）

**目标**：当 LLM 裁判评估不准确时，人工修正评分，提升评估体系可信度。

**步骤**：

1. **发现误判**
   - 查看实验报告中的失败用例
   - 发现某个用例模型输出其实是对的，但评估器给了低分

2. **校准评分**
   - 点击该用例的「校准」按钮
   - 人工给出正确分数（如从 0.3 改为 0.9）
   - 选择是否通过（passed）
   - 填写校准说明（如「模型正确理解了用户意图，评估器误判」）

3. **查看校准后报告**
   - 校准后的报告会优先使用人工校准值
   - 校准率显示有多少结果经过了人工确认
   - 高校准率的实验报告更可信

## 六、最佳实践

### 6.1 数据集构建建议

- **覆盖度**：数据集应覆盖 Prompt 的所有核心能力场景
- **边界用例**：包含困难、歧义、边缘 case，而不仅是简单 case
- **期望输出**：expected_output 应明确、可评判，避免模糊描述
- **规模**：初期 20-50 条，稳定后 100-500 条
- **持续更新**：每月回流新数据，删除过时用例

### 6.2 评估器选择建议

| 评估目标 | 推荐类型 | 说明 |
|---------|---------|------|
| 数学/代码正确性 | `exact_match` | 结果必须完全正确 |
| 信息完整性 | `contains` | 检查关键信息是否出现 |
| 开放式回答质量 | `llm_judge` | 需要语义理解能力 |
| 格式规范 | `regex` | 检查 JSON/XML/特定格式 |
| 语义相似性 | `similarity` | 与参考答案的语义接近度 |
| 安全合规 | `llm_judge` + `regex` | 双层检查 |

### 6.3 实验设计建议

- **控制变量**：对比实验只改一个变量（Prompt 或 模型）
- **多次运行**：关键实验重复运行 2-3 次，排除随机性
- **关注失败用例**：平均分提升 0.1 不如把失败 case 修好更有价值
- **延迟监控**：质量提升但延迟翻倍，需要权衡

### 6.4 Prompt 优化建议

- **先看失败模式**：AI 调优前自己先看失败用例，理解问题本质
- **小步迭代**：每次只改一个方面，方便归因
- **保留旧版本**：优化后保留原版本，方便对比回滚
- **人工审核 AI 建议**：AI 生成的优化建议需要人工检查，确保符合业务逻辑

## 七、常见问题

**Q：实验运行失败怎么办？**
- 检查目标模型的 API Key 是否有效
- 检查模型配置中的 base_url 是否正确
- 查看后端日志获取详细错误信息

**Q：为什么 AI 调优提示"没有低分样本"？**
- 实验必须完成（`completed` 状态）
- 所有用例评分都 ≥ 0.6，说明当前 Prompt 已经足够好，或者评估器太宽松

**Q：回归测试的数据集怎么选？**
- 选择覆盖核心能力的用例（不是越多越好）
- 包含历史上出过问题的 case
- 20-50 条即可，太多会拖慢回归速度

**Q：Prompt 配置选项里的注释会保存到数据库吗？**
- 不会。前端提交时会自动去除注释，只保存纯 JSON 数据到后端。

**Q：温度值设置多少合适？**
- 确定性任务（数学、代码）：0.0-0.3
- 创意任务（写作、头脑风暴）：0.7-1.0
- 客服/问答：0.3-0.7
