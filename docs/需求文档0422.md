## 2. 项目背景与目标

### 2.1 项目背景

AgentMonitor 是一款面向 AI Agent 开发者的质量监控与调试平台。当前版本（v1.0.3）已具备实时监控、断点调试、成本分析、决策追踪等核心能力，支持 TypeScript/JavaScript、Python、Go 三种语言的 SDK 接入。

### 2.2 当前痛点

通过对现有用户（Agent 开发者）的调研分析，发现以下核心痛点：

1. **Prompt 工程黑盒化**：开发者频繁修改 prompt，但缺乏版本管理、A/B 对比和数据回流的闭环工具
2. **测评手段原始**：上线前缺乏系统化的批量评估能力，只能依赖"手动跑几个 case"的主观判断
3. **线上数据浪费**：用户反馈、失败 case、异常 trace 等宝贵数据未被结构化采集并回流到优化环节
4. **Agent 行为不可解释**：ReAct / Multi-Agent 等复杂执行链的可视化程度不足，排查问题效率低

### 2.3 产品目标

**核心目标**：将 AgentMonitor 从"监控工具"升级为 **"Agent 开发全生命周期管理平台"**。

具体指标：
- 覆盖 Agent 开发完整工作流：提示词开发 → 本地调试 → 监控运行 → 测评优化 → 线上数据回流
- 支持 Prompt 版本管理与 A/B 测试，使 prompt 迭代有数据支撑
- 提供自动化评估套件（Eval Suite），让 Agent 上线前有标准化质量 gate
- 构建数据飞轮：线上用户反馈和失败 case 自动归因，并回流到开发优化环节

## 5. 详细需求设计


### REQ-01：Prompt 版本管理（P0）

#### 5.1.1 需求背景

Agent 的核心能力很大程度上取决于 Prompt 的质量。开发者在迭代过程中会频繁修改 prompt，但当前缺乏系统化的版本管理机制，导致：
- 无法追溯"哪个版本的 prompt 效果最好"
- 多人协作时容易互相覆盖 prompt
- 回滚到历史版本困难

#### 5.1.2 用户故事

> **作为** Agent 开发者  
> **我希望** 为我的 Agent 保存不同版本的 prompt，并追踪每个版本的线上表现  
> **以便** 有据可依地选择最佳 prompt 版本，并在需要时快速回滚

#### 5.1.3 功能描述

**核心能力**：
1. **Prompt 注册与版本化**：通过 SDK 或面板注册 prompt，系统自动分配版本号
2. **版本历史查看**：展示 prompt 的完整版本历史，支持 diff 对比
3. **版本效果数据**：每个版本关联线上指标（调用次数、成功率、平均延迟、平均质量分）
4. **版本切换**：支持将线上流量切换到指定版本（与 REQ-02 联动）

#### 5.1.4 详细设计

**数据模型**

```typescript
interface PromptVersion {
  id: string;                    // UUID
  project_id: string;            // 所属项目
  agent_id: string;              // 所属 Agent（可选，一个项目可有多个 Agent）
  version: string;               // 版本号，如 "v1.0.0" 或语义化版本
  name: string;                  // 版本名称（如"增加格式示例"）
  content: string;               // prompt 内容
  variables: string[];           // 提取的变量占位符（如 {{user_input}}）
  metadata: {
    model?: string;              // 关联模型
    temperature?: number;
    max_tokens?: number;
  };
  created_by: string;            // 创建者用户ID
  created_at: string;            // ISO 8601
  is_active: boolean;            // 是否当前线上版本
  metrics: {
    total_calls: number;
    success_rate: number;
    avg_latency_ms: number;
    avg_quality_score: number;
  };
}
```

**SDK API 设计**

```typescript
// TypeScript / JavaScript
monitor.registerPrompt({
  agentId: 'customer-service-bot',
  version: 'v1.2.0',
  name: '增加退款场景示例',
  content: '你是一个客服助手...\n\n用户问题：{{user_input}}',
  metadata: {
    model: 'gpt-4',
    temperature: 0.7,
  },
});

// 在 trace 中关联 prompt 版本
monitor.traceLLM({
  model: 'gpt-4',
  promptVersion: 'v1.2.0',      // 新增字段
  input: {...},
  output: {...},
  latencyMs: 1200,
});
```

```python
# Python
monitor.register_prompt(
    agent_id='customer-service-bot',
    version='v1.2.0',
    name='增加退款场景示例',
    content='你是一个客服助手...\n\n用户问题：{{user_input}}',
    metadata={'model': 'gpt-4', 'temperature': 0.7}
)
```

**REST API 设计**

```
POST   /api/v1/prompts                    # 注册新 prompt 版本
GET    /api/v1/projects/{pid}/prompts     # 获取项目下所有 prompt 版本
GET    /api/v1/prompts/{id}               # 获取单个 prompt 详情
GET    /api/v1/prompts/{id}/diff?compare=v1.1.0   # 对比两个版本
PUT    /api/v1/prompts/{id}/activate      # 设为线上活跃版本
DELETE /api/v1/prompts/{id}               # 删除版本（仅软删）
```

**前端界面**

- **Prompt 管理页** (`/prompts`)：
  - 左侧：Agent 列表树（项目 → Agent）
  - 右侧：选中 Agent 的 prompt 版本列表（表格形式）
  - 表格列：版本号、名称、调用次数、成功率、平均延迟、质量分、创建时间、操作
  - 操作按钮：查看详情、对比、设为活跃、删除
  
- **Prompt 详情弹窗**：
  - 上半部分：元信息（版本号、名称、模型参数、创建者）
  - 下半部分：prompt 内容（语法高亮，变量用不同颜色标注）
  - 底部：该版本的指标趋势图（7天）

- **Diff 对比视图**：
  - 左右分栏展示两个版本的 prompt
  - 行级 diff 高亮（新增绿色 / 删除红色 / 修改黄色）

- [ ] 删除操作仅为软删除，保留数据完整性

### REQ-02：Prompt A/B 测试（P0）

#### 5.2.1 需求背景

Prompt 迭代不能凭感觉，需要数据驱动。A/B 测试是验证 prompt 改进效果的黄金标准。

#### 5.2.2 用户故事

> **作为** Agent 开发者  
> **我希望** 同时上线两个 prompt 版本，自动对比它们的效果  
> **以便** 用数据决定哪个版本更值得全量发布

#### 5.2.3 功能描述

1. **实验创建**：选择基准版本（A）和挑战版本（B），设定分流比例和实验时长
2. **自动分流**：SDK 根据配置自动将流量分配到 A/B 两个版本
3. **实时对比**：面板展示 A/B 版本的实时指标对比
4. **统计显著性**：自动计算指标差异的统计显著性（p-value），避免随机波动误导
5. **实验结论**：实验结束后自动生成结论报告，推荐是否全量

#### 5.2.4 详细设计

**数据模型**

```typescript
interface PromptExperiment {
  id: string;
  project_id: string;
  agent_id: string;
  name: string;                  // 实验名称，如"退款场景优化实验"
  status: 'running' | 'paused' | 'completed' | 'cancelled';
  
  variant_a: {
    prompt_version: string;      // 基准版本
    traffic_percent: number;     // 如 50
  };
  variant_b: {
    prompt_version: string;      // 挑战版本
    traffic_percent: number;     // 如 50
  };
  
  metrics: {
    primary_metric: 'success_rate' | 'quality_score' | 'latency' | 'cost';
    secondary_metrics: string[];
  };
  
  started_at: string;
  ended_at?: string;
  created_by: string;
  
  // 实验结果
  result?: {
    winner: 'a' | 'b' | 'tie' | 'inconclusive';
    confidence_level: number;    // 如 0.95
    improvement_percent: number; // B 相对 A 的提升百分比
    sample_size_a: number;
    sample_size_b: number;
  };
}
```

**SDK 分流逻辑**

```typescript
// SDK 内部自动根据实验配置选择 prompt 版本
const version = monitor.selectPromptVersion({
  agentId: 'customer-service-bot',
  experimentId: 'exp-001',      // 可选，显式指定实验
});

// 返回选中的版本信息，开发者据此构造 prompt
// SDK 自动在 trace 中标记属于 variant_a 还是 variant_b
```

分流算法要求：
- 基于 `session_id` 或 `user_id` 做一致性哈希，确保同一用户始终进入同一分组
- 避免简单随机导致用户前后体验不一致

**统计显著性计算**

- 成功率差异：使用双样本 Z 检验
- 延迟差异：使用 t 检验（Welch's t-test）
- 质量分差异：使用 t 检验
- 置信水平默认 95%，可配置

**前端界面**

- **实验列表页** (`/experiments`)：
  - 表格展示所有实验：名称、状态、A版本、B版本、样本量、结论
  - 操作：查看详情、暂停、结束

- **实验详情页** (`/experiments/:id`)：
  - 顶部：实验配置卡片（名称、状态、分流比例、开始时间）
  - 中部：实时指标对比表格
    | 指标 | A 版本 | B 版本 | 差异 | 显著性 |
    |------|--------|--------|------|--------|
    | 成功率 | 92.5% | 95.1% | +2.6% | ✅ p<0.05 |
    | 平均延迟 | 1.2s | 1.4s | +0.2s | ❌ 不显著 |
  - 底部：指标趋势对比图（双折线，A蓝色/B绿色）

#### 5.2.5 验收标准

- [ ] 面板支持创建、启动、暂停、结束 A/B 实验
- [ ] SDK 支持自动按实验配置分流
- [ ] 同一用户/会话始终进入同一实验组（一致性哈希）
- [ ] 面板展示 A/B 版本的实时指标对比
- [ ] 自动计算并展示统计显著性（p-value）
- [ ] 实验结束后自动生成结论报告

### REQ-03：Prompt 沙盒（P0）

#### 5.3.1 需求背景

开发者在修改 prompt 时，需要快速验证效果。当前必须重新部署 Agent 或修改代码，效率低下。

#### 5.3.2 用户故事

> **作为** Agent 开发者  
> **我希望** 在面板里直接编辑 prompt 并即时测试效果  
> **以便** 快速验证 prompt 修改，无需重新部署代码

#### 5.3.3 功能描述

1. **在线编辑**：在面板中编辑 prompt，支持变量占位符
2. **即时测试**：输入测试变量，直接调用 LLM 查看输出
3. **测试用例管理**：保存常用测试用例，形成回归测试集
4. **批量对比**：一键对比多个 prompt 版本在同一批用例上的表现

#### 5.3.4 详细设计

**前端界面**

- **Prompt 沙盒页** (`/playground`)：
  - 三栏布局：
    - 左侧：Prompt 编辑器（支持 {{variable}} 语法高亮）
    - 中上：变量输入表单（根据 prompt 中占位符自动生成）
    - 中下：模型参数配置（模型选择、temperature、max_tokens）
    - 右侧：输出结果展示区
  - 操作按钮：运行、保存为版本、添加到测试集

- **测试用例管理**：
  - 支持创建测试用例集（Test Suite）
  - 每个用例包含：名称、变量值、期望输出（可选）
  - 支持导入/导出（JSON 格式）

**API 设计**

```
POST /api/v1/playground/run          # 沙盒运行 prompt
Body: {
  prompt: string,
  variables: Record<string, string>,
  model: string,
  temperature?: number,
  max_tokens?: number
}

POST /api/v1/test-suites             # 创建测试用例集
GET  /api/v1/test-suites             # 列表
GET  /api/v1/test-suites/:id         # 详情
PUT  /api/v1/test-suites/:id         # 更新
DELETE /api/v1/test-suites/:id       # 删除

POST /api/v1/playground/batch-run    # 批量运行测试集

  prompt_version: string,
  test_suite_id: string

```

**沙盒运行安全限制**

- 单次运行 Token 上限：默认 4096，可配置
- 运行超时：默认 30 秒
- 每日沙盒调用限额：防止滥用（与项目配额挂钩）
- API Key 级别的 LLM 调用费用由用户自行承担（使用用户配置的 LLM Provider Key）

#### 5.3.5 验收标准

- [ ] 面板支持在线编辑 prompt 并即时运行
- [ ] 自动识别 prompt 中的变量占位符并生成输入表单

### REQ-04：现有功能改进（P1）

#### 5.4.1 Quality 评分体系重构

**现状问题**：
- 速度评分硬阈值不合理：GPT-4 的 2s 和 GPT-3.5 的 2s 质量不同，不能共用阈值
- 成功评分二元制太粗糙：部分失败是预期内的（如用户输入不合法），不应与系统错误同等扣分
- 缺少输出质量维度：当前只监控"有没有出错"，不监控"输出好不好"

**改进方案**：

```typescript
// 新的评分体系
interface QualityScore {
  overall: number;              // 综合评分 0-100
  dimensions: {
    reliability: number;        // 可靠性：成功率加权，区分错误类型
    latency: number;            // 速度：按模型基准线归一化
    cost_efficiency: number;    // 成本效率：单位质量分的成本
    output_quality: number;     // 输出质量：LLM-as-a-Judge（新增）
  };
}

// 错误类型分类（影响 reliability 计算权重）
type ErrorCategory = 
  | 'system_error'        // 系统错误（权重 1.0）
  | 'timeout'             // 超时（权重 0.8）
  | 'validation_error'    // 输入校验失败（权重 0.3）
  | 'user_cancelled'      // 用户主动取消（权重 0.1）
  | 'expected_fallback';  // 预期降级（权重 0.1）
```

**按模型维度的延迟基准**

| 模型 | 优秀 (<) | 良好 (<) | 一般 (<) | 较差 |
|------|---------|---------|---------|------|
| GPT-3.5 | 300ms | 800ms | 2s | >2s |
| GPT-4 | 1s | 2.5s | 5s | >5s |
| GPT-4o | 500ms | 1.5s | 3s | >3s |
| Claude-3.5-Sonnet | 800ms | 2s | 4s | >4s |
| 自定义模型 | 用户配置 | 用户配置 | 用户配置 | 用户配置 |

**LLM-as-a-Judge 输出质量评分**

- 触发条件：随机采样 + 失败 case 必评（避免全量带来的成本）
- 评价维度（可配置）：
  - `relevance`：输出与用户问题的相关度（0-100）
  - `accuracy`：事实准确性（0-100）
  - `completeness`：回答完整性（0-100）
  - `safety`：有害内容检测（0-100，100=完全安全）
  - `format_compliance`：格式符合度（0-100，如 JSON 是否合法）
- 评分模板内置，支持用户自定义

#### 5.4.2 告警系统增强

**降噪机制**：
- 告警聚合窗口：同一 session/agent 在 5 分钟内的同类告警合并为一条
- 告警冷却期：同一规则的告警触发后，10 分钟内不重复触发
- 告警抑制：P0 级告警触发时，自动抑制低优先级同类告警

**根因快照**：
- 告警通知附带：触发时刻的 trace 链接、最近 3 个相关 trace、关键变量值
- 支持配置 webhook 将快照发送到 Slack/飞书/钉钉

**告警分级**：

| 级别 | 条件 | 通知方式 | 示例 |
|------|------|---------|------|
| P0 | 错误率 > 20% 或完全不可用 | 短信 + 邮件 + IM | 服务降级 |
| P1 | 错误率 > 10% 或延迟突增 | 邮件 + IM | 性能退化 |
| P2 | 错误率 > 5% 或成本超标 | IM 通知 | 轻微异常 |
| P3 | 统计阈值触发 | 仅面板记录 | 趋势预警 |

### REQ-08：Agent 行为一致性检测（P1）

#### 5.8.1 需求背景

#### 5.8.2 用户故事

> **作为** Agent 开发者  
> **我希望** 检测我的 Agent 在相同输入下是否输出稳定  
> **以便** 识别不稳定的场景，通过增加 prompt 约束或调整参数来提升一致性

#### 5.8.3 功能描述

1. **稳定性测试**：对同一测试用例运行 N 次（如 5 次或 10 次）
2. **一致性指标**：输出之间的相似度（embedding cosine similarity + 文本匹配）
3. **不稳定标记**：自动标记一致性低于阈值的用例
4. **根因分析**：分析不稳定 case 的特征（是否涉及数值计算、创意生成等）

#### 5.8.4 详细设计

**一致性计算**

```typescript
interface ConsistencyResult {
  case_id: string;
  runs: number;                 // 运行次数
  outputs: string[];            // 各次输出
  
  // 一致性指标
  exact_match_rate: number;     // 精确一致的比例
  semantic_similarity: {        // 语义相似度（基于 embedding）
    mean: number;               // 平均相似度
    min: number;                // 最小相似度
    std: number;                // 标准差
  };
  
  is_stable: boolean;           // 是否稳定（阈值可配置，默认 mean > 0.9）
  
  // 分析
  analysis?: {
    common_prefix?: string;     // 共同前缀
    divergent_points?: string[]; // 分歧点
  };
}
```

**集成方式**

- 作为 Eval Run 的一种子类型（"稳定性测试"）
- 在数据集用例上配置 `stability_runs: 5`
- 在 Eval Run 报告中增加「稳定性」维度

#### 5.8.5 验收标准

- [ ] 支持对单个用例批量运行 N 次

### REQ-11：失败 Case 自动归因与聚类（P1）

#### 5.11.1 需求背景

Agent 上线后会产生大量失败/异常 trace，开发者难以从中快速识别优先修复的问题模式。

#### 5.11.2 用户故事

> **作为** Agent 开发者  
> **我希望** 系统自动帮我归类失败原因，找出最该优先修复的问题  
> **以便** 把有限的时间投入到影响最大的问题上去

#### 5.11.3 功能描述

1. **自动分类**：基于错误类型、异常信息、输入特征自动归类失败 case
2. **归因分析**：对每类失败给出可能根因
3. **优先级排序**：按影响面（失败次数 × 用户数）排序
4. **一键导出**：将某类失败 case 导出为评估数据集

#### 5.11.4 详细设计

**自动分类维度**

| 分类维度 | 说明 | 示例 |
|---------|------|------|
| 错误类型 | 异常类别 | Timeout / 4xx / 5xx / ParseError / ValidationError |
| 失败阶段 | Agent 执行链中的位置 | LLM 调用 / Tool 调用 / 解析输出 / 业务校验 |
| 输入模式 | 导致失败的输入特征 | 超长输入 / 特殊字符 / 空输入 / 多语言混合 |
| 关联 Tool | 如果是 Tool 失败 | get_weather 超时 / search_api 限流 |
| Prompt 版本 | 哪个版本的 prompt | v1.2 的退款场景失败率高 |

**聚类算法**

- 规则引擎优先：基于明确规则的快速分类（如 status code、error message 匹配）
- 相似度聚类：对未规则匹配的 case，使用错误消息和输入的 embedding 进行聚类
- 人工修正：开发者可以手动调整分类结果，系统自动学习

**前端界面**

- **失败分析页** (`/failures`)：
  - 顶部：本周失败总览（次数、类型分布、趋势）
  - 中部：失败类别列表（按影响面排序）
    | 类别 | 失败次数 | 影响用户 | 占比 | 最近出现 | 操作 |
    |------|---------|---------|------|---------|------|
    | get_weather 超时 | 156 | 89 | 35% | 2分钟前 | 查看/导出 |
    | JSON 解析失败 | 98 | 67 | 22% | 5分钟前 | 查看/导出 |
  - 点击类别：查看该类别的典型 case 列表

#### 5.11.5 验收标准

- [ ] 自动对失败 case 进行多维度分类
- [ ] 按影响面排序展示问题优先级
- [ ] 支持查看每个类别的典型 case
- [ ] 支持一键导出为评估数据集
- [ ] 支持开发者手动修正分类

### REQ-12：Prompt 自动优化建议（P2）

#### 5.12.1 需求背景

AgentMonitor 积累了大量数据（失败模式、用户反馈、评估结果），但这些数据尚未被系统化利用来驱动 prompt 优化。

#### 5.12.2 用户故事

> **作为** Agent 开发者  
> **我希望** 系统基于数据自动给出 prompt 优化建议  
> **以便** 更快发现问题并获得改进方向，减少摸索时间

#### 5.12.3 功能描述

1. **模式识别**：基于失败 case 聚类和用户反馈，识别 prompt 的系统性弱点
2. **优化建议**：生成具体的 prompt 修改建议
3. **影响预测**：预估采纳建议后的预期改善效果
4. **Copilot 对话**：支持自然语言询问优化建议

#### 5.12.4 详细设计

**建议生成规则示例**

| 发现模式 | 自动建议 |
|---------|---------|
| 30% 失败是因为输出 JSON 格式不合法 | "建议在 prompt 中增加 JSON 格式示例，并明确要求不要添加 markdown 代码块标记" |
| 用户频繁反馈"回答太简略" | "建议在 prompt 中增加'请提供详细解释，至少包含3个要点'的约束" |
| Tool 选择决策在低置信度时经常错误 | "建议在 tool 选择 prompt 中增加各工具适用场景的对比示例" |
| 退款场景失败率显著高于其他场景 | "退款场景的边界条件处理不足，建议补充以下 case 的示例..." |

**实现方式**

- V1：基于规则的模板生成（确定性、可解释）
- V2：使用 LLM 分析数据并生成建议（更灵活，但需要校验）

#### 5.12.5 验收标准

- [ ] 系统能自动识别高频失败模式并生成建议
- [ ] 建议附带数据支撑（如"30% 的失败"）
- [ ] 支持一键跳转到 Prompt 沙盒验证建议
- [ ] 采纳建议后可追踪实际改善效果

### 6.2 安全需求

| 需求 | 说明 |
|------|------|
| 数据隔离 | 项目间数据严格隔离，A 项目的用户无法访问 B 项目数据 |

| 传输加密 | SDK 到后端、面板到后端全链路 HTTPS |
| 敏感数据脱敏 | 支持配置敏感字段脱敏规则（如手机号、身份证号） |
| 沙盒安全 | Playground 运行有 Token/超时/配额三重限制 |

### 6.3 可靠性需求

| 需求 | 说明 |
|------|------|
| SDK 降级 | SDK 在服务端不可用时自动静默丢弃数据，不影响主业务 |

| 采样兜底 | 服务端过载时，自动提升采样率保护自身 |
| 告警可靠性 | 告警系统自身异常时，通过备用通道（如邮件）通知管理员 |

### 6.4 兼容性需求

| 需求 | 说明 |
|------|------|

| 浏览器兼容 | 面板支持 Chrome/Firefox/Safari/Edge 最新两个主版本 |

## 9. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| Eval Run 的 LLM Judge 成本过高 | 高 | 中 | 支持本地小模型评判、采样触发、用户自配 API Key |
| 数据量暴增影响查询性能 | 高 | 高 | 支持按环境/时间自动归档、冷热数据分离、采样存储 |
| Prompt A/B 分流引入业务风险 | 中 | 中 | 强制最大分流比例限制（如50%）、一键紧急切回 |
| 多 SDK 语言实现进度不一致 | 中 | 中 | TypeScript SDK 先行，Python/Go 滞后 1-2 周 |
| 安全评估误报率高 | 低 | 中 | 人工复核机制、阈值可调、白名单机制 |
